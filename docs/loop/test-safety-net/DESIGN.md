# 測試安全網（第 7 輪）

本輪起源於一次 `/grill-me` 拷問（主題：改善程式架構）。拷問過程把「想改善架構」逐步逼問成
一個更精準的問題，最後的結論不是重構，而是**先補上專案完全缺席的測試**。

## 一、拷問得出的決策

| # | 決策 | 選擇 |
|---|---|---|
| 1 | 真正的痛點 | 「加新功能越來越怕」→ 目標是**降低改動風險**（不是省 token、不是美觀） |
| 2 | 第一步 | **先建測試安全網**（見下方根因） |
| 3 | 覆蓋範圍 | 只保護真正會出事的：路由表 ＋ lang 文案 ＋ 有狀態核心服務 |
| 4 | 測試性格 | **混合**：關鍵回覆鎖字面，其餘鎖行為（改文案不會整片變紅） |
| 5 | 具體清單 | 9 項：handler 路由、store、reminder、birthday、expense、shopping、imagePending、traChoice、lang |
| 6 | 自動化 | **GitHub Actions**：PR 頁面顯示 ✅／❌，merge 前一眼看出安不安全 |
| 7 | 本輪交付 | **純測試網，一行正式程式碼都不改**（對家人正在用的 bot 零風險） |
| 8 | 往後規矩 | 每輪新功能必須附測試且不得刪除 |

## 二、根因：為什麼「怕改」

體檢數據（拷問當下實測）：

| 指標 | 數字 |
|---|---|
| 總程式碼 | 8,100 行 / 29 檔 |
| 最大檔 `lang.js` | 1,180 行、65 個匯出 |
| `handler.js` | 680 行、**83 個 if 分支**（一輪功能就 +7） |
| 重複的排程器 | 5 個服務各寫一套 |
| 每則聊天固定成本 | ≈ 2,000 tokens（14 個工具 schema + 系統提示） |
| **測試** | **0 個** ← 根因 |

前 6 輪其實**每輪都寫了大量測試**（96 項、89 項、69 斷言、162 種攻擊…），但**寫完就丟**，
每輪都要用 `git show HEAD` 重新手工比對「有沒有改壞舊功能」。安全網不存在，所以每次改動都在裸奔。

**本輪的核心洞察：把測試留下來幾乎是零額外成本**——工作本來就在做，只是以前丟掉。

## 三、架構

```
tests/
  helpers.js                  共用地基：把外部世界整個換成假的
  store.test.js               資料層 + KNOWN_KEYS 防漏登記
  handler-routing.test.js     83 條路由互不吃掉
  reminder.test.js            四種週期觸發矩陣 + tick 併發
  birthday.test.js            國曆 + 農曆（閏月/缺日/壞資料）
  expense-shopping.test.js    記帳 + 購物清單
  pending.test.js             拍照按鈕 + 台鐵選站狀態機
  lang.test.js                72 個匯出 × 6 語言結構完整性
.github/workflows/test.yml    PR 自動驗證
```

### `helpers.js` 的隔離手法

- **儲存層整層替換**：services 都用 `store.load(...)` 屬性呼叫，所以直接換掉 `store.load/save`
  就能攔截 → **測試永遠不會讀寫 `data/` 的真實資料**（前幾輪靠「備份還原」，一旦 agent 疏忽就會殘留；
  現在從結構上不可能碰到）。
- **網路全面封鎖**：`global.fetch` 換成會拋錯的替身，任何測試不小心打網路會立刻失敗而不是靜默變慢。
- **固定時鐘**：`store.taipei()` 可注入，測試不會因為「今天幾號」而飄。
- **LINE / AI 皆為替身**：不發真實訊息、不消耗 Groq 額度。

### 混合政策的落實

- **鎖字面**（少數，都是使用者天天看到的）：`/help` 選單、`清除提醒`／`開啟喝水提醒` 的回覆、
  `add()` 對 once／daily 的確認句。
- **鎖行為**（其餘）：路由用 `spyOn` 驗「有沒有呼叫到對的服務方法」，改文案不會變紅。
- **結構完整性**（lang）：72 個匯出 × 6 語言掃描非空、無殘留 `{佔位符}`、無 `undefined`／`NaN`。

### CI 注意事項

Groq SDK 在**載入當下**就驗金鑰，缺了會直接 throw（`handler.js` 連帶爆掉）。
CI 沒有 `.env`，所以 workflow 注入不具效力的假金鑰。這只影響測試設定，未改動正式程式。

## 四、驗證：這張網真的有牙齒嗎

測不出問題的測試等於沒有測試。除了 210 條全綠之外，另外做了**突變測試**——
故意把 `src/` 改壞（都是我們真實踩過的 bug 類型），確認測試會變紅：

| 人為破壞 | 結果 |
|---|---|
| 路由遮蔽：讓「買到 X」被「買 X」吃掉 | ✅ 抓到 |
| 拿掉 `normHM` 時分範圍檢查（`25:00` 死提醒） | ✅ 抓到 |
| 購物清單去重不再去聲調 | ✅ 抓到 |
| 農曆拿掉閏月檢查（生日重複提醒） | ✅ 抓到 |

**4/4 攔下**，且 `src/` 事後完好還原。

另外也驗證了 `store.test.js` 的 KNOWN_KEYS 檢查：臨時放一支引用未登記資料檔的程式進去，
測試立刻變紅並指名該檔案——把「人要記得登記」變成「機器會擋」。

## 五、本輪發現、但**刻意不修**的問題

依「純測試網不碰正式程式碼」的決策，以下只記錄不處理：

- **`src/lang.js` `lunarToday()` 語言路由 bug**（約 843 行）：判斷式為
  `if (code === 'zh-TW' || !LUNAR_TODAY[code])`，而 `LUNAR_TODAY` 只有 `zh-TW`/`vi`/`en` 三把 key，
  因此 `ja`/`th`/`id` 使用者查「農曆」時**拿到中文**，而非全檔其他 getter 一致的「回落 en」慣例。
  不會空字串或 crash（所以結構掃描不會變紅），屬語言路由邏輯錯誤。留待下一輪修正。
