# PRD — 🎂 農曆生日提醒

## 背景與目標
現有生日功能（`src/services/birthday.js`）只認**國曆**（`生日 媽媽 8/15` 存成 `md:'08-15'`），
每年到那個國曆日期就在早安推播提醒。但家裡長輩多半記的是**農曆**生日，越南家人（媳婦）也習慣
用農曆過生日；目前這群人的生日只能硬換算成國曆手動輸入，麻煩又容易記錯或忘了每年閏月會偏移。

目標：新增「農曆生日」記錄方式，記一次農曆月日（如八月十五），bot 每年自動換算成當年正確的
國曆日子，在早安推播當天提醒——**不需要使用者自己每年查農民曆**。

本輪是**接線**：直接呼叫已驗證過的 `src/services/lunar.js` 農曆引擎（PR #12，14 組權威日期
已驗證），不重寫、不改動引擎；聚焦 `birthday.js` 內部擴充。

## 使用者故事
1. 身為會用中文指令的家人，我想用「農曆生日 阿嬤 8/15」記下阿嬤的農曆生日，以便每年到了
   對應的國曆那天，早安推播自動提醒我幫她慶生，不用自己每年換算農民曆。
2. 身為訂閱早安推播、慣用越南語的媳婦，即使我還不會打中文指令，我也希望家人能幫我用
   「農曆生日」記下我的農曆生日，讓每年生日當天我收到的（越南語）早安訊息裡也會提醒到我。
3. 身為記生日的人，我想在「生日清單」裡同時看到國曆與農曆生日的倒數，並清楚標示哪筆是農曆、
   今年對應哪一天國曆，以便一眼分辨、不會記錯類型或搞混日期。

## 範圍

### 要做
- 新增獨立指令記錄農曆生日，與既有國曆 `生日` 指令並存、互不干擾。
- 每日早安推播比對邏輯擴充為同時支援國曆＋農曆生日命中判斷。
- `生日清單` 同時顯示國曆與農曆項目（含農曆換算後的今年國曆日期與倒數天數）。
- `刪除生日 名字` 沿用既有邏輯，同時可刪農曆或國曆紀錄。
- 明確定義閏月、農曆三十缺日（小月）、台越曆法分歧的處理語意（見下方關鍵決策）。

### 不做（範圍外）
- 不支援中文數字日期輸入（如「農曆生日 阿嬤 八月十五」）；v1 只收數字格式（8/15 等）。
- 不支援標記「閏月出生」；使用者只能記正常月份（1–12），不提供閏月選項。
- 不新增 vi 別名指令（如 `sinh nhật âm lịch`）；生日功能整體的越南語化（含指令別名、
  個人化曆法選擇）留給下一輪「生日功能 vi 化」，避免本輪範圍膨脹。
- 不新增 AI 工具；生日功能維持全指令制，不做自然語句觸發（token 節省原則，與既有一致）。
- 不改動 `lunar.js` 引擎、不改 `store.js`（含 KNOWN_KEYS）、不新增資料檔（沿用 `birthdays.json`）。
- 不做「幫使用者判斷該用台灣曆還是越南曆」的語言推斷（見決策 4）。

## 關鍵決策（六項）

**1. 指令格式** — 採**獨立指令**：`農曆生日 名字 日期`（例：`農曆生日 阿嬤 8/15`）。
日期格式沿用既有 `8/15`／`08-15`／`8月15日` 等寫法，僅需月 1–12、日 1–30 合法即可（是否真有
「三十」由當年農曆動態判斷，見決策 3）。
理由：獨立指令不需去解析「生日 阿嬤 農曆8/15」這種前綴混寫（既有 `add()` 用「最後一個 token
當日期、其餘當名字」的簡單規則，若在日期字串裡塞「農曆」兩字容易誤判或需額外剝離邏輯，風險
較高）；獨立指令解析邏輯完全分離，**保證既有 `生日` 指令與 `parseMD()` 零改動、零回歸風險**。
中文數字（「八月十五」）v1 不收：使用頻率低、解析複雜度不成比例，列範圍外。

**2. 每日比對方向與閏月語意** — 每天把「今天」用 `solar2lunar()` 換算成農曆
`{day, month, leap}`，比對使用者存的農曆月/日；**只在 `leap === 0`（正月）時算命中，
閏月出現的同月同日不觸發提醒**（例：生日存「八月十五」，某年有閏八月，只在**正八月十五**提醒，
**閏八月十五不提醒**）。
理由：民俗慣例生日只認正月；每個農曆年一定有對應的正月，不會有「整年都不提醒」的風險；
此方向（國曆→農曆）天然支援跨年、跨閏月比對，不需要反向搜尋。

**3. 農曆三十缺日（小月）** — 採**提前到廿九提醒**：若某年生日所在的農曆月只有 29 天
（無三十），則在「農曆廿九、且廿九是該月最後一天」時視為命中；月份不缺日的年份仍在
「三十」當天提醒。此規則同時套用在「生日清單」倒數換算與「每日推播比對」兩處，確保兩者
語意一致。
理由：與先前功能一致採「絕不漏提醒」的哲學（跳過整年慶生體驗不佳，長輩生日重要）；
代價是需多一次判斷「今天是否為該農曆月最後一天」（用「明天」的農曆日是否等於 1 來判斷），
複雜度可接受、無外部依賴。

**4. 台越兩套農曆** — v1 **統一使用 `TZ_TW`（台灣曆）計算所有農曆生日**，不依記錄者或
訂閱者語言切換，資料也不需存 tz 欄位。
理由：分歧年極罕見（下次落在 2030/2），且本輪不做 vi 指令、無法可靠判斷「這筆生日該用誰的
文化曆法偏好」——用記錄者當下語言推斷容易猜錯（例如中文長輩幫越南媳婦代記，記錄者語言是
中文，但媳婦本人可能希望用越南曆），與其猜錯不如先保持簡單一致，把「個人化曆法選擇」留給
下一輪「生日功能 vi 化」時，讓使用者能明確指定。此為已知邊界風險，列在下方風險段落。

**5. 生日清單的倒數顯示** — 顯示格式比照現有國曆風格加註農曆換算：
`阿嬤：農曆8/15（今年＝國曆 09-25，還有 12 天）`；若换算日期正好是今天，比照現行文字改為
`🎉 就是今天！`。換算規則：
  - 以「今天所在的農曆年」為基準，用 `lunar2solar(day, month, 農曆年, leap=0, TZ_TW)`
    換算出本農曆年生日對應的國曆日期（`leap` 一律傳 0，因 v1 只存正月生日）。
  - 若換算出的國曆日期 **早於今天** → 已過，改用「農曆年 + 1」重新換算，顯示明年那次。
  - 若換算出的國曆日期等於今天 → 顯示 `🎉 就是今天！`（天數 0）。
  - 三十缺日換算沿用決策 3 的「提前到廿九」規則。
  - 防禦：若 `lunar2solar` 回傳 `[0,0,0]`（規格上僅發生於 leap 誤指定，v1 恆傳 0 理論上不會
    觸發，但仍需防禦），該筆顯示為換算異常、不拋例外、不影響清單其餘筆數正常輸出。

**6. AI 工具與 vi 指令** — 不新增 AI 工具（既有生日功能無 AI 工具，維持一致，token 原則）。
vi 別名指令 v1 不做，整包留到下一輪「生日功能 vi 化」（含個人化曆法選擇一起處理，避免本輪
範圍膨脹、也避免決策 4 的簡化在真正做 vi 化時被迫返工）。但**即使沒有 vi 指令，越南家人仍可
被中文使用者用 `農曆生日` 代記**——生日本身無語言限制欄位，早安推播命中時顯示的
`lang.birthdayLine()` 一樣依訂閱者（可能就是這位越南語使用者本人）既有語言機制呈現，
不受本輪影響。

## 功能需求

- **F1 新增農曆生日**：`農曆生日 名字 日期` → 存入農曆月/日（決策 1）；成功回覆需標示
  「農曆」字樣，並附今年（或明年，若已過）對應國曆日期與倒數天數（沿用決策 5 換算邏輯）。
  日期不合法（月/日超出範圍、看不懂格式）→ 回覆錯誤提示，不寫入。
- **F2 同名覆蓋規則**：沿用既有邏輯——同一使用者、同名字的紀錄，新增（不論國曆或農曆）即
  覆蓋舊紀錄，維持「一人一筆生日」的既有唯一性（不因新增農曆功能而允許同名字同時存在
  國曆＋農曆兩筆）。
- **F3 生日清單**：`生日清單` 指令不變（觸發詞相同），輸出中農曆項目加「農曆」前綴標示、
  並顯示「今年＝國曆 MM-DD」（決策 5）；排序規則不變（依剩餘天數由小到大，國曆／農曆
  混合排序）。
- **F4 每日比對（早安推播命中）**：`todays(userId)` 對外介面與回傳型別**不變**（仍回傳
  「今天生日」姓名陣列），內部擴充為同時比對國曆與農曆紀錄（決策 2、3），`morning.js`
  呼叫端不需改動。
- **F5 刪除**：`刪除生日 名字` 不變，可刪除農曆或國曆紀錄（純按名字比對，無需分類型）。
- **F6 資料相容**：沿用 `birthdays.json`；新增農曆紀錄需以獨立欄位區分於既有 `md`
  （欄位命名由開發者決定，例如另闢 `lm`/`isLunar` 之類），**不得覆用或改寫 `md` 語意**；
  舊資料 `{userId, name, md}` 格式紀錄的讀取與行為必須逐字不變。
- **F7 曆法**：所有農曆換算固定用 `TZ_TW`（決策 4），資料不需存 tz 欄位。

## 驗收條件（皆須可測試驗證）

1. **新增**：`農曆生日 阿嬤 8/15` → 回覆含「農曆」字樣、今年對應國曆日期、剩餘天數；
   非法日期（如 `農曆生日 阿嬤 13/40`）→ 錯誤提示、不寫入 `birthdays.json`。
2. **清單倒數**：混合國曆＋農曆資料時，`生日清單` 中農曆項目標示「農曆」前綴並顯示
   「今年＝國曆 MM-DD」；今天恰為某筆農曆生日對應日 → 顯示 `🎉 就是今天！`；排序按剩餘
   天數正確（國曆／農曆混排）。
3. **刪除**：`刪除生日 阿嬤` 可刪除以農曆方式新增的紀錄；找不到時回覆與現行文字一致。
4. **當天推播命中**：用已知「農曆↔國曆」對照日期（可取自 `lunar.js` 已驗證的權威對照組）
   模擬 `store.taipei()` 的今天，`todays(userId)` 在對應國曆當天回傳含該姓名的陣列；
   非對應日期不回傳。
5. **閏月語意**：構造某年有「閏X月」的情境；當天為「閏X月十五」、使用者記錄「X月十五」
   → **不命中**；當天為「正X月十五」→ **命中**。
6. **三十缺日語意**：構造某年「X月」只有 29 天（無三十）的情境，使用者記錄「X月三十」
   → 當天農曆為「X月廿九」且為該月最後一天 → **命中**；同一規則套用在清單倒數換算的結果
   一致（顯示的「今年＝國曆」日期需等於廿九當天的國曆日期，不是虛構的三十）。
7. **台越 tz 語意**：分別以 zh 與 vi 語言的使用者身分新增相同農曆生日 → 換算出的國曆日期
   一致（皆用 `TZ_TW`），不因使用者語言不同而產生不同結果。
8. **舊資料相容**：手動放入僅含 `{userId, name, md}` 的舊格式紀錄（無新增欄位）→
   `生日清單`、`todays()`、`刪除生日` 對此筆的行為與本次改動前完全一致（逐字比對）。
9. **既有國曆不回歸**：現有 `生日`、`生日清單`、`刪除生日`、`todays()` 對純國曆資料的輸出，
   與本次改動前的既有測試逐字相同（含 `parseMD`、`daysUntil` 行為不變）。
10. **KNOWN_KEYS 不變**：`store.js` 的 `KNOWN_KEYS` 仍只含既有 `birthdays.json`，未新增檔案。
11. **防禦**：注入會讓 `lunar2solar` 回傳 `[0,0,0]` 的異常資料 → 該筆顯示換算異常提示，
    不拋例外、不中止整個清單／推播的其餘輸出。
12. **收斂**：`node --check` 全變更檔通過；測試不 `require index.js`、不 `.start()`、不發真
    LINE 訊息、結尾 `process.exit(0)`、碰 `data/` 需備份還原且逐字驗證還原正確。

## 邊界與風險
- **外部依賴**：零新增（不新增 API 金鑰、套件、資料檔）；僅呼叫既有已驗證的 `lunar.js`。
- **曆法分歧風險**：v1 固定用 `TZ_TW`，下次台越農曆分歧年約在 2030/2；若剛好有生日落在
  分歧區間，換算結果可能與越南曆差一天。機率極低、影響小，先接受此風險，待「生日功能
  vi 化」整包時再考慮個人化曆法選擇。
- **範圍外事項**：不支援中文數字日期、不支援標記閏月出生、不支援 vi 指令別名——這些若使用者
  提出需求，需另開下一輪處理。
- **`lunar2solar` 有效範圍**：引擎保守有效範圍 1900–2199；本功能只換算「今年／明年」，
  遠在範圍內，無風險。
- **效能**：每筆農曆生日在新增／清單／每日推播時會呼叫 1–2 次農曆換算（純數學運算、無
  I/O），家庭用戶規模下無效能疑慮。
- **資料相容風險**：新增欄位務必與既有 `md` 欄位語意分離，否則會污染既有國曆資料判讀
  （對應驗收條件 8、9）。
