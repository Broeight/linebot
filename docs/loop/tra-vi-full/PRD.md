# PRD — 台鐵查詢結果越南語完整在地化（去除中文夾雜）

**版本** v1.0 | **狀態** 待架構師評審 | **相關前作** `docs/loop/tra-train/`、`docs/loop/tra-train-fix/`、`docs/loop/vi-round3/`（F3 已用 `typeEn` 暫時頂著車種翻譯，本次是補完）

---

## 一、背景／目標

本 bot 是家庭共用的 LINE 機器人，使用者橫跨**中文**與**越南語**（越南家人陳氏梅是主要越南語使用者）。台鐵時刻查詢是她常用的功能之一（上下班、返鄉都要查車）。

目前越南語使用者查台鐵班次有兩條路徑，**都不是完整越南語**：

- **路徑 A（AI 工具，站名清楚時）**：`get_tra_train` → `getTraTrainSummary` 回英文摘要 → 交給 Groq 模型即時改寫成越南語。會翻，但（1）非決定性、品質不穩（2）每次都消耗 Groq token，而本專案已知有「免費版每日 token 額度」痛點（3）模型偶爾漏字、殘留中文。
- **路徑 B（點選單按鈕完成查詢）**：`getTraTrainByIds({code:'vi'})`。即使傳了 `code:'vi'`，以下仍是**寫死的中文**，完全不受 `code` 影響：
  - 標頭「🚆 台鐵」「🚆 下一班」
  - 「之後的班次：」
  - 車次號後綴「次」（如「256次」）
  - 「發車」「抵達」
  - 結尾「資料來源：台鐵 TRA（交通部 PTX）」

  且車種名（自強／莒光／區間…）目前用的是英文 `typeEn`（如 `Local`、`Tze-Chiang Limited Express`），**不是越南語**——這是 `vi-round3` 當時的權宜作法，本次要補上真正的越南語。

這是使用者實際抱怨的直接命中點：路徑 B 是**決定性、免 AI**的輸出，理應能保證 100% 越南語，卻仍中文夾雜。

**目標**：讓路徑 B（點按鈕完成查詢）的輸出對越南語使用者是**完整越南語**，不殘留任何寫死的中文字。同時評估是否值得讓路徑 A 也走同一套決定性格式器（見「次範圍」）。

---

## 二、使用者故事

1. 身為越南家人陳氏梅，當我用越南語問台鐵班次、系統跳出「您是指哪一站？」讓我點按鈕選站後，我想看到**完整越南語**的班次列表（車次、車種、發車/抵達時間、行駛時間），以便我不用拜託家人翻譯就能自己判斷要搭哪一班車。
2. 身為越南家人陳氏梅，當今天或明天已經沒有班次時，我想看到用越南語清楚告知「沒有班次」，而不是看到中文夾在越南語句子中間、不確定是不是系統壞了。
3. 身為中文使用的家人，我想在這次改動之後，查台鐵時看到的中文回覆內容跟以前**一模一樣**（逐字不變），以便我不會因為文案被順手改掉而困惑。

## 三、範圍

### 3.1 主範圍（必做）

把 `getTraTrainByIds`（點按鈕完成查詢那條路，路徑 B）的輸出做成對 `code:'vi'` 完整越南語：
- 所有現況寫死中文的字串（標頭、「之後的班次：」、「次」、「發車」「抵達」、「資料來源」）都要依語言在地化。
- 車種名要有真正的越南語對照，不再借用英文 `typeEn` 頂著（`typeEn` 仍保留給 `code:'en'` 用）。

**建議一併處理（低風險，同一根因）**：上述寫死中文字串目前的判斷式是「`zh-TW` 用中文，其餘語言全部共用同一份中文」，也就是說 **`code:'en'` 現在其實也是中文夾雜**（只有車種名走英文 `typeEn`，標頭／「次」／發車抵達／資料來源都還是中文）。既然要把判斷式從「zh-TW vs 其他」改成「依語言分流」，建議把 `en` 一併補成完整英文（可直接沿用 `getTraTrainSummary` 已經在用的英文措辭，如 `Source: Taiwan Railway (TRA) via MOTC PTX.`、`departs`/`arrives`、`No.{trainNo}`，零額外設計成本、風格一致）。此項為建議，非強制，但若不做，至少要滿足底下「硬性約束」的 en 不回歸。

### 3.2 次範圍（建議納入，交由架構師判斷可行性與回歸風險——本 PRD 不預先鎖定實作）

讓 AI 工具路徑（路徑 A，`get_tra_train` → `getTraTrainSummary`）對 `vi`／`en` 使用者也走同一套決定性越南語／英語格式器，繞過模型改寫時刻表本體內容。

好處：
- 保證不漏中文（決定性輸出，不靠模型「盡量翻好」）。
- **直接緩解已知的 Groq 每日 token 額度痛點**——時刻表改寫是相對「重」的一段文字，若能省下模型改寫這段，可望減少 token 消耗。

風險（列給架構師評估，不在此 PRD 訂實作方式）：
- 會動到 `src/tools.js` 的 `get_tra_train` case 與其回傳給模型的契約格式（目前是給模型一段英文摘要讓它自由轉述），改成決定性格式後，模型可能只能在前後加一句招呼語，對話語氣的彈性會變小。
- 需確認不影響 `NEEDS_STATION_CHOICE`／`traChoice` 選站狀態機（那是另一條分支，理論上不受影響，但需回歸測試）。
- 既有測試（`tra-train`、`tra-train-fix`、`tra-voice-choice`、`vi-friction`、`vi-round3` 系列）可能需要更新預期字串。
- Token 節省量無法在 PRD 階段量化（目前沒有埋點），需架構師估算或事後量測。

### 3.3 範圍外（明確不做）

- **不翻譯站名**：時刻表起訖站名（台北、新竹…）維持中文，見 §4.3 決策理由。越南語別名標註（如「Đài Bắc (台北)」）列為 nice-to-have，是否做、怎麼做交由架構師判斷，不在本次驗收範圍。
- **不做 ja/th/id 的完整台鐵在地化**：這三個語言目前經由既有 fallback 規則會與 `en` 走同一分支；本次改動後會「順帶」自然拿到英文而非殘留中文，但不額外開發、不額外測試要求，也不允許因此變差。
- **不新增任何 API 金鑰、不新增外部相依**。
- **不改變查詢邏輯**：快取（30 分鐘）、逾時（6 秒）、排序、每次最多 5 筆、跨午夜行駛時間計算方式，一律不動。
- **不改日期顯示順序**：`MM/DD` 格式維持現況、不因語言改變順序（避免與既有中文指令路徑 `lookup()`/`nextTrain()` 的既有格式不一致）。
- 不做歷史班次查詢、轉乘規劃等新功能。

## 四、功能需求

### 4.1 主範圍：字串在地化清單

以下是 `getTraTrainByIds` 目前寫死中文、且不受 `code` 影響的項目，逐項要能依 `code` 切換成對應語言（`vi` 為必做；`en` 為建議一併做，見 §3.1）：

| # | 用途 | 現況（zh-TW，逐字不可變）| 出現在 |
|---|---|---|---|
| 1 | 列表標頭 | 「🚆 台鐵」 | 列表模式（有班次／已無班次兩種情況都會出現）|
| 2 | 下一班標頭 | 「🚆 下一班」 | `nextOnly` 模式（有班次／已無班次兩種情況都會出現）|
| 3 | 班次時間段落標題 | 「之後的班次：」 | 列表模式、有班次時 |
| 4 | 車次計次詞 | 「次」（如「256次」）| 兩種模式、有班次時 |
| 5 | 發車／抵達 | 「發車」「抵達」 | `nextOnly` 模式、有班次時 |
| 6 | 資料來源行 | 「資料來源：台鐵 TRA（交通部 PTX）」 | 兩種模式、有班次時 |
| 7 | 車種名 | 目前非 zh-TW 一律用 `typeEn`（英文），不是越南語 | 兩種模式、有班次時 |

既有已經做好、**不需改動、只需回歸驗證**的部分：
- 「今天／明天」「已無班次」整句（`WHEN_LABEL`／`NO_TRAINS`／`whenLabel`／`noTrainsText`）。
- 行駛時間單位在地化（`durationLocalized`：vi 為「X giờ Y phút」、en 為「XhYm」）。

`SOURCE` 常數本身（`'台鐵 TRA（交通部 PTX）'`）**不可更動**，因為 `lookup()`／`nextTrain()`（中文指令路徑）仍在用它、且不受本次影響。`getTraTrainByIds` 需為非中文語言另外組出對應語句，不可直接沿用同一顯示字串。

全形括號、全形空格、「・」項目符號、🚆／⏰ 等表情符號**不算中文字**，各語言皆可沿用現有排版，不在「不得含中文」的檢查範圍內；驗收時只檢查 CJK 表意文字（漢字本身），不檢查標點與符號。

### 4.2 車種對照表（zh → vi）

台鐵常見車種約 8–10 類。PTX 回傳的 `typeZh` 有時會帶額外括注細節（例如實際觀察到的「自強(3000)」「自強(推拉式自強號且無自行車車廂)」「普悠瑪(普悠瑪)」），因此對照邏輯**必須能把帶括注的變體歸類到同一個基準車種**，不能只做完全相等比對，否則絕大多數班次都會落回 fallback。

以下為 PM 草案，供架構師／實作者參考，**精確用字（含聲調、慣用說法）建議請越南語母語者複核**；驗收條件不鎖死逐字字面，只鎖「同一基準車種永遠映射到同一個非中文、非空白的越南語字串」：

| PTX `typeZh` 基準（含常見括注變體）| PTX `typeEn`（既有）| 建議越南語 |
|---|---|---|
| 自強（含「自強(3000)」「自強(推拉式…)」等）| Tze-Chiang / Tze-Chiang Limited Express | Tàu Tự Cường (tốc hành nhanh nhất) |
| 太魯閣 | Taroko / Taroko Express | Tàu Taroko (tốc hành nhanh) |
| 普悠瑪（含「普悠瑪(普悠瑪)」等）| Puyuma / Puyuma Express | Tàu Puyuma (tốc hành nhanh) |
| 莒光 | Chu-Kuang / Chu-Kuang Express | Tàu Chu-Kuang (tốc hành) |
| 復興 | Fu-Hsing | Tàu Phục Hưng (tốc hành chậm) |
| 區間快 | Local (Fast) / Region Express | Tàu địa phương nhanh (dừng ít ga hơn) |
| 區間（含「區間車」）| Local / Local Train | Tàu địa phương (dừng nhiều ga) |
| 普快（含「普快車」）| Ordinary / Local | Tàu thường (chậm nhất) |

**回落策略（必做，功能需求，不預設實作方式）**：
1. 查得到對照 → 用越南語對照。
2. 對照表查無此車種（新車種、PTX 命名變動）→ 回落 `typeEn`（英文，至少不是中文）。
3. 連 `typeEn` 都沒有 → 回落 `typeZh`（中文，最後手段）。
4. 永不回傳空字串／`undefined`。

### 4.3 站名處理決策

**決策：時刻表起訖站名維持中文（如「台北」「新竹」），不翻譯成越南語。**

理由：這是實用性考量——使用者到了車站現場，月台、車廂看板、廣播、站牌指示都是中文，維持中文站名才能讓使用者對照現場找到正確的車、正確的月台。翻成越南語反而在現場沒有對應依據，可能造成混淆。

越南語別名附註（例如顯示成「Đài Bắc (台北)」）列為 **nice-to-have**，是否加、加在哪個位置（標頭或每一筆班次都加）交由架構師評估必要性與畫面雜訊的取捨，不在本次驗收範圍內。輸入端的越南語站名辨識（`VN_ALIAS` 模糊比對、選單按鈕）已存在且運作正常，本次不變動。

## 五、驗收條件（Acceptance Criteria）

每條都要可被測試員照著跑一次就驗證通過或失敗。

| # | 情境／輸入 | 預期輸出重點 | 通過標準 |
|---|---|---|---|
| AC-01 | `getTraTrainByIds({...})` 不傳 `code`，或傳 `code:'zh-TW'`；涵蓋「有班次列表」「`nextOnly:true` 有班次」「今日已無班次」「明日已無班次」四種情境 | 輸出與**修改前**逐字（byte-identical）相同 | 用修改前的輸出當 golden string 比對，四種情境全部逐字相同，一個字元都不能差 |
| AC-02 | `code:'vi'`，起訖站有多筆（≤5）班次的列表情境 | 整段輸出**不含任何中文字（CJK 表意文字）**，除了 `fromName`/`toName` 這兩個依 §4.3 決策刻意保留中文的站名 token；含正確日期（MM/DD）、越南語標頭、越南語「之後的班次」句、每筆含車次號（非中文計次詞）、越南語車種名、正確的 `→` 時間段、越南語行駛時間（「X giờ Y phút」）、越南語資料來源整行 | 逐項檢查全部符合；排除 `fromName`/`toName` 後對全文跑 CJK 字元正則掃描，結果為 0 個中文字 |
| AC-03 | `code:'vi'`，`nextOnly:true`，有 1 筆有效班次 | 同 AC-02 的「無中文殘留」規則，且含越南語版「發車」「抵達」對應詞、越南語下一班標頭 | 同上檢查方式 |
| AC-04 | `code:'vi'`，`day:'today'`，今日已無班次 | 標頭部分也是越南語（不再只有 `noTrainsText` 那句是越南語、標頭卻殘留中文）；含既有的 `hôm nay` / 「Không còn chuyến tàu nào…」 | 無中文殘留檢查 + 含既有 `noTrainsText('vi', false)` 的既定輸出 |
| AC-05 | `code:'vi'`，`day:'tomorrow'`，明日已無班次 | 同 AC-04，含 `ngày mai` | 無中文殘留檢查 + 含既有 `noTrainsText('vi', true)` 的既定輸出 |
| AC-06 | 車種對照：至少涵蓋 §4.2 表列的 8 個基準車種，以及至少 2 組「同基準、不同括注」的變體（如「自強(3000)」vs「自強(推拉式自強號且無自行車車廂)」；「普悠瑪」vs「普悠瑪(普悠瑪)」）| 同一基準車種的所有變體，映射出**相同**的越南語字串；字串非空、非 `typeZh` 原樣照抄 | 用 fixture 資料（不需真打 PTX，可自建 mock 班次陣列）驗證映射一致性 |
| AC-07 | 車種對照缺漏：模擬一個不在對照表中的全新 `typeZh`（如虛構「城際特快」）| 依序回落：優先 `typeEn`（若該筆 fixture 有給）；沒有 `typeEn` 才回落 `typeZh`；不得回傳空字串或 `undefined` | fixture 驗證兩種回落情境各一次 |
| AC-08 | 跨午夜班次：`code:'vi'`，一筆發車 22:01、抵達 00:24 的班次（可用既有 `tra-train` TEST.md 記錄過的真實案例）| 越南語行駛時間輸出為「2 giờ 23 phút」 | 直接驗證 `durationLocalized('vi', '22:01', '00:24')` 或整段組字後的行駛時間字串 |
| AC-09 | `code:'en'` 涵蓋列表／`nextOnly`／今日無班次／明日無班次四種情境 | 至少：既有行為不回歸（`typeEn` 車種、既有英文 `whenLabel`/`noTrainsText`）；若採用 §3.1 建議一併修正，則標頭／「次」／發車抵達／資料來源也需為英文、無中文殘留 | 若未採用建議修正：以修改前輸出逐字比對車種與 when 相關片段不變；若採用建議修正：跑與 AC-02 相同的「無中文殘留」規則（排除站名）|
| AC-10 | `code:'ja'`／`'th'`／`'id'` 各跑一次列表情境（任一即可）| 不因本次改動而變差；若走與 `en` 相同分支，允許自然變成英文，但不得停留在「殘留中文」的現況 | 手動確認輸出無崩潰、無 `undefined`；不要求特定語言的完整在地化 |
| AC-11 （若採用 §3.2 次範圍）| `get_tra_train` 呼叫端（`tools.js`）對 `vi`/`en` 使用者查詢 | 時刻表本體內容不再經模型自由改寫（以 monkeypatch 計數 `ai`/Groq 呼叫驗證：呼叫次數不因本次改動而增加，理想為此段不再需要模型改寫）| monkeypatch 驗證；具體降低多少次由架構師 DESIGN 文件定義 |
| AC-12 （若採用 §3.2 次範圍）| 既有測試回歸 | `tra-train`／`tra-train-fix`／`tra-voice-choice`／`vi-friction`／`vi-round3` 系列測試重新執行 | 全數通過，或每一處預期字串變更都有清楚記錄與理由 |

### 測試紀律（本專案鐵律，測試員需遵守）

- 測試腳本**不得** `require index.js`。
- **不得**呼叫任何 `.start()`。
- 測試腳本結尾**必須** `process.exit(0)`。
- **不得**發送真實 LINE 訊息（`client.pushMessage`／`replyMessage` 一律 stub/monkeypatch）。
- 若測試流程會碰到 `data/` 下的檔案（例如經 `lang.resolve()` 間接寫入 `data/lang.json`），**必須**先備份、測試後還原，並逐字（byte-identical）驗證還原成功。**建議**：測試直接對 `getTraTrainByIds({..., code})` 傳入 `code` 參數即可涵蓋所有情境，完全不需經過 `lang.resolve()`，可避免碰觸 `data/`。
- 所有變更檔案 `node --check` 須全部通過。

## 六、邊界與風險

- **外部 API**：本次不新增任何外部 API 或金鑰；PTX 端點、逾時（6 秒）、快取（30 分鐘）行為維持不變。
- **Token 額度（次範圍相關）**：主範圍完全不呼叫模型，零額外 token 消耗。次範圍若採用可望降低 Groq token 消耗，但目前無埋點可量化，需架構師事後量測或估算。
- **語言涵蓋**：`zh-TW`/`vi`/`en` 為本次確定要處理的語言；`ja`/`th`/`id` 允許順帶受益（跟著落到 `en` 分支）但不強制、不額外測試。
- **資料儲存**：`getTraTrainByIds` 本身是無狀態查詢函式，不寫入 `data/*.json`。唯一可能碰觸 `data/` 的是測試若透過 `lang.resolve()` 取得 `code`（見「測試紀律」）；建議測試直接傳入 `code` 參數以避免此風險。
- **車種對照缺漏**：PTX 車種命名可能隨時間新增或微調文字（如新車型上線、既有車種改名），對照表需要能優雅回落（見 §4.2 回落策略），不可讓「查無對照」變成中文殘留或程式錯誤。
- **跨午夜行駛時間**：既有 `duration()`/`durationLocalized()` 已處理「抵達時間 < 出發時間視為 +24 小時」，本次不重新設計，只需驗證越南語呈現正確（見 AC-08）。
- **站名越南語別名缺漏**：因決策維持中文站名（§4.3），此風險本次不適用；未來若做 nice-to-have 別名標註，才需處理「查無別名時怎麼顯示」。
- **次範圍的契約與回歸風險**：已列於 §3.2，重申——這是「建議評估」而非本 PRD 鎖定的必做項，架構師可決定本輪只做主範圍、次範圍另開一輪。

## 七、PM 建議（次範圍是否值得做）

**建議：值得做，但可以分兩輪。** 本輪先把主範圍（路徑 B，決定性輸出）做完、做穩，這是使用者實際回報的痛點，風險最低、效益最直接。次範圍（讓 AI 工具路徑也走決定性格式器）效益也很吸引人——尤其「省 Groq token」直接命中本專案已知的額度痛點——但它牽動 `tools.js` 的工具契約與模型對話語氣，屬於「值得做、但要小心做」的類型。建議主範圍先上線驗證穩定後，再開一輪次範圍，讓架構師針對「模型契約怎麼改」「既有測試怎麼更新」給出明確設計，而不是在同一輪一次吃下兩種風險層級不同的變更。
